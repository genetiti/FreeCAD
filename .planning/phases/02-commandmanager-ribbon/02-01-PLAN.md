<objective>
Stand up the Wave 0 test scaffold AND run the time-boxed native-Qt ribbon spike that resolves the D-01/D-02/D-03/D-04 native-vs-SARibbon decision (CONTEXT D-02/D-03/D-04, RESEARCH "Spike Plan"). This is the first vertical slice: a thin, real `FwRibbon` (`QTabWidget` hosting `QToolBar` panels of large labeled buttons) built from a small known set of real command IDs, proving every D-03 parity primitive works on native Qt 6.8 before the full build commits. The spike's exit criteria make the native-vs-fallback choice explicit and actionable: PASS → SPIKE.md records "native committed" and native is the committed engine for Plans 02-02/02-03/02-04; FAIL → trigger the pre-blessed SARibbon fallback (D-04) and re-scope.

Purpose: De-risk the highest net-new-risk part of the milestone (Roadmap note: "native-vs-SARibbon decision must resolve before downstream tab-switching depends on it") and establish the headless test harness all later ribbon plans sample against.
Output: `FwRibbon.{h,cpp}` (minimal but real), a shared `FwTestGuiBootstrap.h` (QApplication + module-GUI-command load), command-ID resolution tests in `Gui_tests_run` (`FwRibbon.cpp`) and a QWidget-construction Qt test (`FwRibbonWidget.cpp`, `QTEST_MAIN`/offscreen) wired via `setup_qt_test`, CMake additions, and `SPIKE.md` recording the D-03 verdict.

> **Test-harness correction (REVIEW concerns 1 & 2 — load-bearing):** The original plan put all FwRibbon tests in `Gui_tests_run`. Two facts in this checkout make that wrong: (1) `Gui_tests_run` has NO `QApplication` (verified: `tests/CMakeLists.txt` — only `setup_qt_test` targets get a Qt main via `QTEST_MAIN`); constructing `FwRibbon : QTabWidget` there fails. (2) `PartDesign_*`/`Sketcher_*` commands are registered by `CreatePartDesignCommands()` inside `PartDesignGui`'s module init (verified: `src/Mod/PartDesign/Gui/AppPartDesignGui.cpp:122`), NOT by linking `FreeCADGui`; no existing test loads a module GUI, so `getCommandByName("PartDesign_Pad")` returns nullptr in a bare target. This plan splits tests accordingly: pure command-ID resolution after an explicit module-GUI load (GTest), and widget construction under an offscreen `QApplication` (Qt test).
</objective>
