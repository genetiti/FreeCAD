Deliver the PROP-01 core vertical slice: when a feature/sketch command or edit starts, the PropertyManager appears **left-docked** with a green-✓ accept / red-✗ cancel header, and the hosted task panel (rollouts, fields, live preview) runs **unmodified** inside it — end to end, non-modal — and **the chrome SURVIVES the edit-time workbench switch** so a tree double-click lands left WITH the header (R3-ROOT). The keystone is `FwLayout::mountPropertyManager()`: at FreeWorks activation, place the managed PropertyManager dock (identity `"Tasks"` — the live container objectName `getDockWindow("Tasks")` resolves and `Control::taskPanel()` reads, Control.cpp:55-61 / DockWindowManager.cpp:325) into `Qt::LeftDockWidgetArea`.

**The mount mechanism is the R2-F1 correction.** `addDockWindow("Tasks", taskView, Left)` will **NOT move an already-docked Tasks panel** — `DockWindowManager::addDockWindow()` returns the existing dock immediately when `widget->parentWidget()` is already a `QDockWidget` (DockWindowManager.cpp:256-258), *before* the `mw->addDockWidget(pos, dw)` placement (:278) and the objectName-set (:290), both of which run only on the NEW-dock branch. Stock/PartDesign workbenches dock Tasks on the **right** via `Std_TaskView` (Workbench.cpp:925, `Qt::RightDockWidgetArea`), so coming from such a workbench `Control().taskPanel()` is non-null inside an existing right `QDockWidget` that `addDockWindow` would never move. So `mountPropertyManager()` resolves the host from `Gui::Control().taskPanel()`, walks **up** to its parent `QDockWidget`, and branches on `getMainWindow()->dockWidgetArea(dock)`: (a) if a parent `QDockWidget` exists and is **not** left, call `Gui::getMainWindow()->addDockWidget(Qt::LeftDockWidgetArea, dock)` **directly** to re-dock the existing container left (the came-from-right-dock case); (b) **only** when `taskPanel()` has no parent `QDockWidget` (never-docked — true in FreeWorks mode where `FwWorkbench::setupDockWindows()` never returns `Std_TaskView`, FwWorkbench.cpp:95-124, F1) resolve the registered Tasks `TaskView` via `findRegisteredDockWindow("Std_TaskView")` and create it left via `addDockWindow("Tasks", taskView, Qt::LeftDockWidgetArea)` (on the NEW-dock branch this sets the container objectName to `"Tasks"`, :290, so `getDockWindow("Tasks")` resolves). The host is resolved **robustly** — never a hardcoded `getDockContainer("Std_TaskView")` guess.

**The placeholder removal is the R3-MAJOR3 correction.** The Phase-3 pre-setup `unregisterDockWindow("Fw_PropertyManager") + deleteLater()` pattern is WRONG in this post-setup case: `DockWindowManager::setup()` already created a LIVE `QDockWidget` from the registered `Fw_PropertyManager` placeholder (DockWindowManager.cpp:529), so by mount time the placeholder is inside a live dock; `unregisterDockWindow()` only removes registry state (:495) while deleting the widget triggers async dock deletion via `onWidgetDestroyed()` (:668), leaving a stale second left surface. Pick ONE correct disposition and assert the post-state: (i) **stop contributing** `Fw_PropertyManager` before `DockWindowManager::setup()` (FwWorkbench::setupDockWindows() no longer addDockWidget("Fw_PropertyManager",...) at FwWorkbench.cpp:117, and FwLayout::install() no longer registers the placeholder at FwLayout.cpp:162-175 when the Tasks host occupies the left slot); OR (ii) **remove the live dock explicitly** via `DockWindowManager::instance()->removeDockWindow(getDockWindow("Fw_PropertyManager"))`. The QTEST asserts NO `QDockWidget` named `Fw_PropertyManager` remains after mount, so exactly ONE left PropertyManager exists — the `"Tasks"` dock (R2-F3).

**The teardown is the R3-ROOT / R4-BLOCKER correction (the 04-01 A4 verdict — a DEFERRED, CANCELLABLE teardown, NOT a pre-checked flag).** `Application::activateWorkbench()` calls `oldWb->deactivated()` (Application.cpp:1984) **before** `newWb->activated()` (:2006), and PartDesign `setEdit()` calls `assureWorkbench("PartDesignWorkbench")` (ViewProvider.cpp:165) **before** `Control().showDialog()` (:175) — Sketcher edit does the same via SketcherWorkbench (ViewProviderSketch.cpp:635); `signalInEdit` fires only after `startEditing()` (Document.cpp:680-692). An unconditional `unmountPropertyManager()` would strip the header/key-filter/styler so the edit lands in a left RAW Tasks dock without the FreeWorks chrome (R3-BLOCKER2).
