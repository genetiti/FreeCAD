<objective>
Deliver PROP-02 (the pink active selection-reference box) and D-10 (SolidWorks keyboard/focus semantics) on top of the left-hosted panel from Plan 04-02 — and ensure both the styler and the key filter (FreeWorks CHROME on the host) SURVIVE the edit-time workbench switch so a tree double-click lands left WITH them (R3-ROOT/R3-BLOCKER2/R4-BLOCKER, the 04-01 A4 verdict).

First, deliver the pink active tone **through a QPalette role** as D-06 (locked) requires (R2-F6 VERIFIED): a bare `activeReferenceBoxTone()→QColor` accessor while `FwTheme::apply()` stays no-op does **not** satisfy "via a QPalette role" — and `QPalette::Highlight` is the system highlight (typically blue, NOT pink, FwFeatureTreeDelegate.cpp:154-159), `FwTheme::apply()` is currently a no-op (FwTheme.cpp:31-39). So **`FwTheme::apply()` becomes functional**: it installs the single FreeWorks-owned pink VALUE into a chosen `QPalette` ROLE (named by the 04-01 SPIKE A3 verdict) on the reference-box widget's **local** palette (QPalette has no custom roles, so the pink is carried on the box widget's own palette via the chosen role, reversibly). The pink VALUE lives **once** in `FwTheme` (a private constant the `apply()` path writes into the role — the only literal site; Phase 7 refines the hue here). `FwReferenceBoxStyler` reads the active tone as `widget->palette().color(<role>)` — a real QPalette-role read, not an accessor-equality call — so "no hex in the styler" AND "via a QPalette role" both hold.

`FwReferenceBoxStyler` is a thin FreeWorks styler that applies that role tone to exactly the ONE reference box the user has clicked into — and reverts it on deactivate (restoring the prior palette) — while the box's actual picking machinery (fill on pick, highlight, auto-expand, clear/remove) stays OWNED by the hosted panel's `Gui::SelectionFilterGate` + `Gui::SelectionObserver` (e.g. `PartDesignGui::ReferenceSelection`). The styler READS which box is active per the 04-01 SPIKE A3 verdict (R2-F4 VERIFIED: `Gui::Selection` exposes only a selection-gate pointer; the real two-field active state `TaskPatternParameters::activeDirectionWidget` is private at TaskPatternParameters.h:91, with two real direction widgets at .h:88-89 — so a focus+selection-only styler can color the wrong real box). The recorded mechanism is therefore either a developer-approved `// SW-FORK HOOK` active-field accessor on the hosted panel, or focus inference **validated against the real `TaskPatternParameters` panel**. It restyles only; it never builds a parallel selection backend (D-05 — Phase 5 owns selection), and it holds NO color literal of its own (the pink VALUE lives only in `FwTheme`).

`FwPropertyKeyFilter` is a thin container-level `QObject` event filter that guarantees Enter→`Control().accept()`, Escape→`Control().reject()`, and Tab→advance to the next reference box — reusing `TaskView`'s existing Enter/Esc mapping and adding only the SW Tab-between-boxes traversal, scoped to top-level fields so it never fights the hosted panel's internal focus chain (Pitfall 5) or pushes focus out into the 3D view.

**Survivability (R3-ROOT / R3-BLOCKER2 / R4-BLOCKER).** Both the styler and the key filter are FreeWorks chrome mounted on the host. A synchronous `unmountPropertyManager()` on the per-edit transient `deactivated()` (which fires DURING the `assureWorkbench`/Sketcher-edit round-trip — Application.cpp:1984 before :2006; ViewProvider.cpp:165 before :175; ViewProviderSketch.cpp:635), OR one gated on a pre-checked edit-in-progress flag that is still FALSE at that instant because `signalInEdit` has not yet fired (Document.cpp:680-692 — R4-BLOCKER), would STRIP them, so a tree double-click would land in a left RAW Tasks dock without the pink styler / key filter — failing PROP-02/D-10 in the exact round-trip the plans fix. So the styler + key filter are installed by `mountPropertyManager()` and released ONLY by the 04-02 DEFERRED-CANCELLABLE teardown (the A4 policy: `deactivated()` SCHEDULES a `QTimer::singleShot(0)` teardown, `signalInEdit` — fired after `startEditing`, within the same synchronous event-loop turn — or the FreeWorks re-`activated()` CANCELS it before it runs) — they SURVIVE the edit-time WB switch and release only when a genuine no-edit FreeWorks→stock switch leaves the queued teardown uncancelled.

**Buildable real-panel QTEST (R3-MAJOR5).** `setup_qt_test()` links only `FreeCADApp`/`FreeCADGui`/QtTest (tests/CMakeLists.txt:27); `PartDesignGui` is a separate shared target (src/Mod/PartDesign/Gui/CMakeLists.txt:242), so directly including/constructing `TaskPatternParameters` may fail to link. The plan default is BLACK-BOX: after `ensureGuiTestBootstrap()` imports PartDesignGui, drive the real linear-pattern command/panel and locate the two direction-widget instances through the live `qApp` widget tree (`findChildren`/`allWidgets`) — NO direct include/construct — so the test is buildable without a CMake link change. (Alternatively the QTEST may link `PartDesignGui` via `setup_qt_test` extra-libs and construct directly; pick one and state it in the SUMMARY.)

Purpose: These two are the genuinely-new behaviors of the phase (04-PATTERNS § No Analog Found: "the only genuinely-new behavior is the active-box-pink state machine and the container key filter") — both have a structural analog (palette-role paint; scoped-signal lifetime) even though the behavior is new. PROP-02's pink active-state and D-10's SW keys complete the panel's *feel* on top of the 04-02 host. Making `FwTheme::apply()` functional (populate the role) makes the "no hex in the styler, via a QPalette role, never blue" rule actually implementable (R2-F6), proving the styler against the real `TaskPatternParameters` 2-field panel via a buildable linkage ensures it colors the RIGHT box (R2-F4/R3-MAJOR5), and keeping the styler + key filter under the 04-02 deferred-cancellable teardown ensures they survive the edit-time WB switch (R3-ROOT/R4-BLOCKER).
