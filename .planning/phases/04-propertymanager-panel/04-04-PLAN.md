<objective>
Deliver the two glue requirements that complete the SolidWorks modeling loop on top of the left-hosted panel: **TREE-03** (double-click a tree feature → edit it in the left PropertyManager) and **FLOW-01** (sketch → feature handoff).

**TREE-03 is the R3-MAJOR4 correction.** The generic "`ViewProviderDocumentObject::doubleClicked → setEdit`" wording was WRONG. The real route: `TreeWidget` calls `vp->doubleClicked()` (Tree.cpp:2148); the BASE `Gui::ViewProvider::doubleClicked()` returns `false` (ViewProvider.h:700); the CONCRETE `PartDesignGui::ViewProvider::doubleClicked()` override (ViewProvider.cpp:91) opens a command and calls `Gui::cmdSetEdit(pcObject, getUserEditMode())` (ViewProvider.cpp:95-96) → `Gui::Document::setEdit()` → the VP's `setEdit()`/`Gui::Control().showDialog()`. Because that dialog shows via `Gui::Control` (D-01) and Control's TaskView is left-hosted (Plan 04-02), the edit panel lands LEFT automatically — so this plan only *proves* the CONCRETE route reaches `cmdSetEdit`/`setEdit` and lands left, adding no new edit dispatcher. The probe MUST exercise a REAL PartDesign feature VP (e.g. a Pad), NOT a generic editable VP whose base `doubleClicked()` returns false.

**FLOW-01 is the R3-BLOCKER1 correction.** The sketch-exit selection handler must NOT hang off the transient-teardown `FwRibbonContext`/`s_ribbonContext`. `FwWorkbench::deactivated()` calls `FwLayout::unmountRibbon()` (FwWorkbench.cpp:66/71) which does `s_ribbonContext.reset()` (FwLayout.cpp:286), and a sketch edit transiently activates `SketcherWorkbench` (ViewProviderSketch.cpp:635) so `deactivated()` fires (Application.cpp:1984 before :2006) BEFORE `signalResetEdit` (Document.cpp:747-750) — so a FLOW-01 handler on the `s_ribbonContext` `signalResetEdit` consumer (FwRibbonContext.cpp:111-121) would be DESTROYED before sketch exit fires (the isolation test passes while the product fails). So the FLOW-01 PERSISTENT-sketch-select step rides the 04-02 SURVIVABLE reveal/edit-in-progress consumer (`s_propertyReveal`, owned by its OWN `unique_ptr` static separate from `s_ribbonContext`, surviving the edit-time WB switch per the 04-01 A4 verdict). On a sketch reset, set the just-finished sketch as the current `Gui::Selection` (so a subsequent Extrude/Revolve picks it up as the profile) — but **do NOT auto-start** a feature command (D-11). The Features-tab restore STAYS on `FwRibbonContext` (the ribbon-tab owner, a cosmetic nicety) where it already lives; only the survivability-critical selection step moves. Sketch identity is the existing `"SketcherGui::ViewProviderSketch"` type-name literal (no Sketcher link — Pitfall 2).

**CRITICAL (F5 + R2-F7):** the selection change must be **persistent** — do NOT wrap it in `FwSelectionGuard`, whose destructor clears selection and restores the snapshot on scope exit (FwSelectionGuard.cpp:89-123), which would UNDO the just-set sketch selection (a false-pass: the `addSelection` grep still matches while FLOW-01 actually fails). Use a persistent `Gui::Selection().clearSelection(/*pDocName=*/nullptr, /*clearPreSelect=*/false)` + `addSelection(doc, sketch, /*pSubName=*/nullptr, 0,0,0, /*pickedList=*/nullptr, /*clearPreSelect=*/false)`. R2-F7: `clearSelection(const char* = nullptr, bool clearPreSelect = true)` (Selection.h:385) clears preselect **by default** — pass `clearPreSelect=false` to PRESERVE a live preselect; and the persistent `addSelection` overload is at **Selection.h:336-345** (NOT line 360, the `addSelection(const SelectionObject&, bool)` overload).

**CRITICAL (R2-F8 + R3-BLOCKER1):** prove FLOW-01 by testing the SURVIVABLE FreeWorks reset handler **in isolation**, NOT by driving a real `ViewProviderSketch` reset. `SketcherGui::ViewProviderSketch::unsetEdit()` already clears selection and selects the edited sketch (ViewProviderSketch.cpp:4263-4264) **before** `signalResetEdit` is emitted (Document.cpp:747-750), so a post-reset "sketch is selected" assertion would FALSE-PASS even if the handler does nothing. The test pre-clears selection, invokes the survivable handler directly, asserts IT sets the sketch selection and that the selection PERSISTS after the handler scope returns; ALSO simulates a transient `deactivated()`/`s_ribbonContext.reset()` before the selection action and asserts the handler STILL runs (it is on the survivable `s_propertyReveal`, not the reset `s_ribbonContext` — R3-BLOCKER1); the ribbon Features-tab landing is asserted separately.

Purpose: This is the final vertical slice that makes the phase a complete SolidWorks loop — pick a plane → Sketch (panel opens left) → draw → exit (sketch auto-selected even through the edit-time WB switch, Features tab ready) → Extrude (panel opens left, edit lands left); double-clicking any tree feature re-opens its edit left via the concrete PartDesign route. Both reuse existing seams (the inherited tree double-click → concrete PartDesign override; the 04-02 survivable consumer) — no new mechanism (04-RESEARCH § Don't Hand-Roll: "a new edit dispatcher" and "auto-launching a feature command" are explicit anti-goals).
Output: the FLOW-01 extension to the 04-02 survivable `s_propertyReveal` consumer in `FwLayout.{h,cpp}` (the persistent sketch-select step, NO FwSelectionGuard, clearPreSelect=false on both calls — R2-F7, no auto-launch, off the transient s_ribbonContext — R3-BLOCKER1), the documented decoupling of the selection step from `FwRibbonContext` (which keeps only the cosmetic tab restore), the FLOW-01 GTest in `FwPropertyManager.cpp` (handler-in-isolation + persistence + survivability assertions — R2-F8/R3-BLOCKER1), and the TREE-03 CONCRETE-route QTEST in `FwFeatureTreeWidget.cpp` against a real PartDesign feature VP (R3-MAJOR4).
